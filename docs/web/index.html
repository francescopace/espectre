Build with the SDK

ESPectre's sensing core is a reusable C++ layer. Link it into any ESP-IDF firmware and your product gains motion sensing — the Wi-Fi radio it already has is the sensor.

// your_firmware.cpp
#include <espectre/sensing.h>

espectre::Sensor sensor;

void app_main() {
  sensor.begin();  // uses the existing Wi-Fi stack
  sensor.on_motion([](float score) {
    // blender detects a person → wake the UI
    display.wake();
  });
}

Guides / Hardware
HARDWARE · 6 MIN READ

Choose your hardware

Any supported ESP32 works. This guide helps you pick a board that senses well, and explains what actually affects detection quality.

Supported chips

All chips below run every published firmware (ESPHome, Native, and Matter) and use the same detection pipeline. Differences are practical, not functional.

ChipPractical notes
ESP32-C3Small, inexpensive, and everywhere. The easiest starting point: a C3 devkit or super-mini board costs a few euros.
ESP32-C6The most recent radio generation. A good default if you are buying new hardware today.
ESP32-S3The most compute headroom, useful if the board will also do other work. Many S3 devkits expose an external antenna connector.
ESP32 (classic)Widely available and well supported. Fine for reusing boards you already own.
ESP32-C5Dual-band capable; ESPectre senses on 2.4 GHz. Note: USB Wi-Fi provisioning in the flasher is not available yet on C5.

What actually matters

  • The antenna. Boards with an external antenna connector (U.FL/IPEX) give a cleaner, more stable signal than tiny PCB antennas, especially at longer range. It is the single most effective hardware upgrade.
  • The power supply. A stable 5 V USB supply matters: cheap noisy chargers show up as radio noise. If readings look erratic on a good placement, try another power adapter first.
  • Placement beats hardware. A mediocre board placed well outperforms a great board inside a metal cabinet. Keep the sensor 3–8 m from the access point, in the room you want to monitor. The detection guide covers placement in detail.
  • The USB cable. For flashing you need a data cable; for permanent installs any power-only cable is fine.

Shopping checklist

  • A devkit-style board with native USB for one of the chips above (search for "chip name devkit").
  • Optionally, a version with an external antenna connector plus a 2.4 GHz antenna.
  • A known-good USB data cable and a decent 5 V power supply.
  • No other sensors, shields, or modules: the Wi-Fi radio is the sensor.
One board covers one area, typically a room. For multiple rooms, use one sensor per room; every published firmware handles multiple devices side by side.

Building ESPectre into a product?

If your device already contains a supported ESP32, its radio can double as a motion sensor without adding hardware: the sensing engine embeds into existing ESP-IDF firmware, and the published firmwares serve as reference integrations. Start from the custom firmware guide and the embedding guide; licensing options are described in the licensing overview.

Guides / Flash & Wi-Fi setup
SETUP · 8 MIN READ

Flash and set up your device

This tutorial takes you from a blank ESP32 board to a working motion sensor. No toolchain, no compiler: everything happens in the browser.

What you need

  • An ESP32, ESP32-C3, ESP32-C5, ESP32-C6, or ESP32-S3 board.
  • A USB cable that carries data, not only power. If in doubt, try another cable first: it is the single most common problem.
  • Chrome or Edge on desktop. Browser flashing uses Web Serial, which Firefox and Safari do not support.
  • The name and password of your 2.4 GHz Wi-Fi network. ESP32 boards cannot join 5 GHz-only networks.

Step 1 — Choose your firmware

Pick the row that matches how you want to use the sensor. You can always reflash later; switching firmware takes two minutes.

If you...FlashYou get
Want a standalone sensor with browser tools or MQTTNativeBluetooth setup page, MQTT telemetry, live monitor, and the browser games
Use Home AssistantESPHomeAuto-discovered device with motion, movement level, threshold slider, and recalibrate switch
Use Apple Home, Google Home, Alexa, or SmartThingsMatterA standard occupancy sensor you add by scanning a QR code
Want raw CSI data for researchStreamerRaw capture over UDP; not flashable from the browser, see the custom firmware guide
Not sure? Pick Native, the default in the flasher: it works on its own and you can try every tool on this website. If you run Home Assistant, pick ESPHome instead.

Step 2 — Flash from the browser

  1. Plug the board in

    Connect the ESP32 to your computer over USB. Close anything that may be using the serial port, such as a previous flasher tab, the Arduino IDE, or a serial monitor.

  2. Open the flasher

    Go to the Flash page, keep Latest Release selected, and choose the firmware from Step 1 and your chip family. The chip name is usually printed on the module itself (for example ESP32-C3).

  3. Connect

    Click Connect. The browser shows a list of serial ports: pick the one that appears when you plug the board in (on Windows a COMx port, on macOS/Linux something like usbserial, usbmodem, or ttyACM).

  4. Install

    Choose Install, confirm, and wait. Flashing takes one to three minutes; do not unplug the cable. When it finishes, the device reboots into ESPectre.

If the port never appears or the connection fails right away, hold the BOOT button on the board while plugging the cable in, then release it and click Connect again. That forces the chip into download mode.

Step 3 — Connect it to your network

This step depends on the firmware you flashed.

Native

  1. Open the Configure page

    Go to Configure in Chrome or Edge and click Connect. Pick the ESPectre BLE device from the Bluetooth list. The board must be powered but does not need Wi-Fi yet.

  2. Save Wi-Fi and MQTT

    Enter your network name and password. If you have an MQTT broker, add its host and port to get telemetry; if not, you can skip it and the sensor still works over Bluetooth.

  3. Watch it live

    Use the same Configure page to see the live movement bar, or open the Monitor to chart MQTT telemetry from the browser.

ESPHome

  1. Configure Wi-Fi in the flasher

    Right after installation, the same dialog offers Configure Wi-Fi. Enter your 2.4 GHz network name and password. On ESP32-C5 this dialog is not available yet: connect to the ESPectre Fallback hotspot the device creates and enter the credentials there.

  2. Add it in Home Assistant

    Within a minute, Home Assistant shows a notification for a discovered ESPHome device. Accept it, and you get the motion sensor, movement level, threshold control, and recalibrate switch.

Matter

  1. Get the QR code

    After flashing, the flasher shows the device's Matter QR code and manual pairing code. Each device has its own code, and reflashing does not change it, so you can save it.

  2. Add the device in your app

    In Apple Home, Google Home, Alexa, or SmartThings choose Add device and scan the QR code. Keep the phone near the board: commissioning starts over Bluetooth, then the device joins your Wi-Fi.

  3. Place it in a room

    The device appears as an occupancy sensor. Use it in automations exactly like any other motion sensor.

Step 4 — Let it calibrate, then test

  • After joining Wi-Fi, the sensor calibrates its quiet baseline. This takes roughly ten seconds with the default settings: keep the room still, then move normally.
  • Wave an arm a few meters from the board: the motion state should turn active within about a second and clear shortly after you stop.
  • If you later move the device to another room or position, trigger a recalibration (Home Assistant switch, Configure page, or just power-cycle it).
The movement level is a 0.0–1.0 score specific to your room. If the sensor is too eager or too lazy, adjust the threshold slightly instead of expecting one universal value: the detection guide explains what the numbers mean.

Troubleshooting

No serial port appears

  • Try another USB cable: charge-only cables are the top cause.
  • Try another USB port, ideally directly on the computer.
  • Hold BOOT while plugging in, then retry Connect.

Flashing starts but fails midway

  • Close other tabs or programs using the port and retry.
  • Use a rear USB port or a powered hub: unstable power interrupts flashing.
  • Retry with Erase enabled to start from a clean flash.

Device will not join Wi-Fi

  • Confirm the network is 2.4 GHz; guest and 5 GHz-only networks fail.
  • Re-enter the exact SSID and password: both are case-sensitive.
  • Move the board closer to the access point for the first join.

Matter commissioning times out

  • Keep the phone within a meter of the board while pairing.
  • Make sure the phone's Bluetooth is on and the board is powered.
  • Power-cycle the board to reopen the commissioning window, then retry.

Native is not publishing MQTT

  • Check broker host, port, and credentials in Configure.
  • Confirm the broker is reachable from the device's network.
  • Use the Monitor to see whether telemetry arrives.

Motion triggers with nobody there

  • Recalibrate with the room genuinely empty and still.
  • Raise the threshold a little.
  • Check for fans, curtains moving in airflow, or pets: the sensor sees them too.

CLI flashing (fallback)

If browser flashing does not work on your system, clone the repository and flash with the ESPectre CLI. After ./espectre doctor succeeds, build and flash the frontend you chose in Step 1:

./espectre native build --chip c3
./espectre native flash --port /dev/cu.usbmodemXXXX

Use esphome or matter instead of native when that is your firmware. Full prerequisites and command reference are in the setup reference; the custom firmware guide walks through the same local workflow.

Guides / How detection works
THEORY · 12 MIN READ

How motion detection works

What the movement score actually measures, what happens during calibration, and how to place and tune the sensor so it behaves well in your room.

The idea in one minute

Wi-Fi signals reach the ESP32 over many paths at once: direct, bounced off walls, furniture, and people. Each received packet carries Channel State Information (CSI), a per-subcarrier measurement of how the radio channel looked at that instant. When nobody moves, those measurements are remarkably stable. When a person moves, the reflected paths change and the measurements start to scatter. ESPectre measures that scatter, on the device, packet by packet.

The signal path

Everything below runs on the ESP32. No raw radio data leaves the device; only the derived score and motion state are published.

Wi-Fi packets2.4 GHz traffic
CSI captureSubcarrier samples
ConditioningNormalize and filter
DetectionClassic or ML
OutputScore and motion

Conditioning matters because raw CSI is noisy: gain normalization compensates for the receiver's automatic gain control, a Hampel filter drops isolated outliers, and an optional low-pass filter removes fast noise while keeping the slower variations caused by human movement.

What the numbers mean

  • Movement score (0.0–1.0): how strongly the channel is changing right now. It is a room-specific signal, not a physical unit: 0.3 in your living room and 0.3 in your office are not the same thing.
  • Threshold: the score level that counts as motion. Classic adapts it during calibration; you can adjust it at runtime from Home Assistant, the Configure page, or MQTT.
  • Motion state: turns on after the score stays above the threshold for a few consecutive evaluations (about one second at default settings) and off after it stays below (slightly faster). This hit filter is why a single spike does not trigger a false alarm.
  • Calibration: at startup the detector learns the quiet baseline of your room, which takes roughly ten seconds at the default packet rate. Keep the room still while it runs, and recalibrate whenever you move the device.

Classic or ML?

Classic (default)ML
How it decidesFuses two channel features into a motion probabilitySmall neural network over a six-feature window
Training dataNone neededShips with a pre-trained model
ThresholdSelf-calibrated per session, adjustableFixed default (0.5), adjustable
Best forMost rooms; transparent and lightweightExperiments with learned decision boundaries

Both run entirely on the ESP32, use the same 0.0–1.0 scale, and can be switched at runtime on ESPHome and Native firmware. Start with Classic; try ML if you are curious or your room proves difficult.

Placement that works

  • Keep the sensor roughly 3–8 meters from your Wi-Fi access point. Too close risks receiver saturation; too far means a weaker, noisier signal.
  • Put it in the room you want to monitor, where people cross the space between the router and the sensor or move near the device.
  • Do not enclose it in a metal cabinet or press the antenna against a large metal surface.
  • Keep the room still during the ten-second startup calibration.
  • Moved the device? Recalibrate. Placement changes the baseline more than any parameter does.

Quick tuning recipe

Triggers with nobody there

  • Raise the threshold a little.
  • Recalibrate with the room genuinely empty.
  • Look for fans, curtains in airflow, or pets: the sensor sees them too.

Misses real motion

  • Lower the threshold a little.
  • Check placement: distance from the AP and obstacles matter most.
  • Verify the device receives steady traffic (the built-in traffic generator keeps ~100 packets/s by default).
Wi-Fi sensing detects changes in the radio environment. It does not identify people, count them, or replace a safety-certified presence sensor.

Build a frontend from source

  1. Clone and check the environment

    Clone the repository, create the virtual environment, and run the doctor command: it verifies Python, ESP-IDF, and the serial tooling before your first build. Native, Matter, and Streamer need a working ESP-IDF installation; ESPHome installs its own toolchain.

  2. Build for your chip

    Every frontend builds through the same wrapper; pick the chip explicitly.

  3. Flash and watch the logs

    Each build command has a matching flash/monitor flow; use --help on any subcommand for current options and port naming.

git clone https://github.com/francescopace/espectre.git
cd espectre
./espectre doctor

./espectre esphome build --chip c3
./espectre native build --chip c3
./espectre matter build --chip c3
./espectre streamer build --chip c3 --clean

./espectre native flash --port /dev/cu.usbmodemXXXX
./espectre monitor --port /dev/cu.usbmodemXXXX

Full prerequisites and command reference: SETUP.md and CLI.md.

Streamer credentials are supplied at build time and Streamer binaries are not published by the browser flasher. Never commit local Wi-Fi or MQTT secrets.

Embed ESPectre in an existing firmware

The reusable C++ layers let an ESP-IDF product own boot, networking, storage, OTA, and UI while ESPectre supplies the sensing path. The embedding guide documents the layers, the runtime contracts, and the build integration in detail.

  1. Connect CSI capture

    Feed compatible ESP32 CSI frames into the shared capture and processing boundary, or let the ESPectre runtime own capture entirely.

  2. Select the reusable layers

    Use the core directly for the smallest integration, or reuse the runtime services when you also want lifecycle and orchestration.

  3. Map product events

    Translate movement score, motion state, calibration state, and diagnostics into the product's existing event system.

  4. Validate in context

    Measure CPU, memory, packet flow, reconnect behavior, and detection quality inside the complete product firmware.

ESPectre exposes reusable source layers rather than a precompiled binary SDK, and it is dual-licensed: GPLv3 for open-source firmware, with commercial licenses available for embedding into proprietary products.

Before you ship

  • Build the exact chip and frontend combination you will deploy.
  • Run the shared C++ detection tests after changing core algorithms.
  • Verify first boot, provisioning, reconnect, and recovery on physical hardware.
  • Measure motion behavior in the intended room, not only on the bench.

API reference

The sensing surface an embedding firmware talks to. One sensor object, a callback, and a handful of runtime controls — the layers below (capture, conditioning, detection) are reusable source, not a binary blob.

Lifecycle

#include <espectre/sensing.h>

espectre::Sensor sensor;

void app_main() {
  sensor.begin();          // attach to the existing Wi-Fi stack
  // ... your firmware keeps running as usual
  sensor.stop();           // detach cleanly when needed
}
MethodWhat it does
begin()Starts CSI capture on the already-initialized Wi-Fi stack and runs startup calibration (~10 s of quiet baseline).
stop()Stops capture and releases the CSI callback. Safe to call from your shutdown path.
recalibrate()Re-learns the quiet baseline. Call it when the device is moved or the room changes.

Events

sensor.on_motion([](float score) {
  // fired when motion state turns on
});

sensor.on_telemetry([](const espectre::Telemetry& t) {
  // t.movement, t.threshold, t.motion — every evaluation
});
FieldTypeMeaning
movementfloatMovement score, 0.0–1.0, room-specific.
thresholdfloatCurrent motion threshold on the same scale.
motionboolDebounced motion state after the hit filter.

Runtime controls

MethodWhat it does
set_threshold(float)Overrides the motion threshold at runtime (0.0–1.0).
set_detector(Detector)Switches between Classic and Ml at runtime.
diagnostics()Returns capture rate, calibration state, and filter configuration for your own health reporting.

Examples

Each published frontend doubles as a reference integration. Start from the one closest to your product.

Minimal sensor

The smallest useful integration: begin, react to motion, done. This is the pattern for products that just need a wake-up or presence signal.

sensor.begin();
sensor.on_motion([](float score) {
  display.wake();          // your product logic here
});

MQTT node

Publish telemetry into an existing MQTT stack using the shared protocol shape, so tools like the Monitor work out of the box. Reference: the Native frontend (src/cpp/frontend/native/).

sensor.on_telemetry([](const espectre::Telemetry& t) {
  mqtt.publish(topic + "/telemetry", to_json(t));
});

Matter occupancy sensor

Map the debounced motion state onto a Matter occupancy cluster, and the device shows up in Apple Home, Google Home, Alexa, and SmartThings. Reference: the Matter frontend (src/cpp/frontend/matter/).

sensor.on_motion([](float) {
  occupancy_cluster.set(true);
});

Custom detector experiments

The detection layer is swappable: the Streamer frontend exports raw CSI over UDP so you can prototype features and detectors in Python before porting them to C++. Reference: src/cpp/frontend/streamer/ and the ML training workflow.

Docs / Architecture
SDK · ARCHITECTURE

Architecture

Three layers, one rule: everything below the frontend is reusable and platform-clean. Your product replaces the frontend; the sensing stays the same.

The layers

Frontends src/cpp/frontend/
ESPHome · Native · Matter · Streamer — or your product firmware. Owns boot, networking, UI, and integration surface.
Runtime src/cpp/runtime/
Platform-agnostic contracts: capture lifecycle, calibration, telemetry, transports. ESP-IDF specifics live in runtime/esp_idf/.
Core src/cpp/core/
The algorithms: CSI conditioning, features, Classic and ML detectors. Pure C++17, no SDK includes, mirrored by the Python R&D implementation.

Why it is shaped this way

  • Core is header-clean. Nothing in core/ or runtime/ includes ESP-IDF: the same code runs in firmware and in host-side tests.
  • Python first, C++ to ship. Algorithms are prototyped and validated in Python (src/python/), then ported to the shared C++ layers with matched behavior and shared test baselines.
  • Frontends are thin. Each one maps the same sensing pipeline onto a different integration surface — Home Assistant entities, Matter clusters, MQTT topics, or raw UDP.
  • License boundary. Core, runtime, and the native/Matter/streamer frontends stay free of GPL-only dependencies so the dual-licensing model works; only the ESPHome frontend depends on ESPHome's GPL components.
