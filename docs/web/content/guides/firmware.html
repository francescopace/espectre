Build a frontend from source

  1. Clone and check the environment

    Clone the repository and create the virtual environment. Native, Matter, and Streamer prefer local ESP-IDF and automatically use the pinned Docker build environment when it is absent; ESPHome installs its own toolchain. Flashing from the CLI still uses local ESP-IDF and serial tooling.

  2. Build for your chip

    Every frontend builds through the same wrapper; pick the chip explicitly.

  3. Flash and watch the logs

    Each build command has a matching flash/monitor flow; use --help on any subcommand for current options and port naming.

git clone https://github.com/francescopace/espectre.git
cd espectre
./espectre doctor

./espectre esphome build --chip c3
./espectre native build --chip c3
./espectre matter build --chip c3
./espectre streamer build --chip c3 --clean

./espectre native flash --port /dev/cu.usbmodemXXXX
./espectre monitor --port /dev/cu.usbmodemXXXX

Full prerequisites and command reference: SETUP.md and CLI.md.

Streamer credentials are supplied at build time and Streamer binaries are not published by the browser flasher. Never commit local Wi-Fi or MQTT secrets.

Embed ESPectre in an existing firmware

The reusable C++ layers let an ESP-IDF product own boot, networking, storage, OTA, and UI while ESPectre supplies the sensing path. The embedding guide documents the layers, the runtime contracts, and the build integration in detail.

Choose the detector against the complete product budget

Lightweight is the leaner production profile: it leaves more CPU time and working memory for connectivity, OTA, UI, or other application services, at the cost of lower detection accuracy and generalization. High Accuracy provides higher detection quality but maintains more feature state and runs neural inference. Lightweight adapts its threshold during up to about 10 seconds of quiet startup calibration and can still lower it after a later quiet stretch; High Accuracy skips that calibration, although it still waits for CSI readiness and feature-window warmup. Mirror on_threshold_changed() if the product publishes a writable threshold control.

Both profiles are available through the SDK. Select the initial path with RuntimeConfig::detection_algorithm. Expose runtime switching only when the product needs it; including both paths can retain ML code and weights in flash even when Lightweight is active. Use the profile guide as the product-level decision reference.

Designed beyond today's ESP32 CSI APIs

Today's firmware captures CSI through the APIs available on supported ESP32 devices. IEEE 802.11bf-2025 standardizes WLAN mechanisms for advertising sensing capabilities, coordinating sensing measurements, and exchanging sensing feedback. ESPectre does not currently implement 802.11bf.

The separation between detector core, runtime, events, protocols, tooling, and frontends provides a migration boundary for future hardware. If an embedded vendor exposes practical 802.11bf measurements, or an equivalent documented sensing API, ESPectre can evaluate it as a new runtime backend without replacing the product-facing integration above it. Hardware support, measurement semantics, and detector quality would still require validation before that backend could be considered supported. The roadmap records this as a hardware-triggered direction rather than a release commitment.

  1. Connect CSI capture

    Feed compatible ESP32 CSI frames into the shared capture and processing boundary, or let the ESPectre runtime own capture entirely.

  2. Select the reusable layers and profile

    Use the core directly for the smallest integration, or reuse the runtime services when you also want lifecycle and orchestration. Choose Lightweight or High Accuracy from the measured resource and detection-quality budget of the complete firmware.

  3. Map product events

    Translate movement score, motion state, live threshold, calibration state, and diagnostics into the product's existing event system.

  4. Validate in context

    Measure CPU, memory, packet flow, reconnect behavior, and detection quality inside the complete product firmware.

ESPectre exposes reusable source layers rather than a precompiled binary SDK, and it is dual-licensed: GPLv3 for open-source firmware, with commercial licenses available for embedding into proprietary products.

Before you ship

  • Build the exact chip and frontend combination you will deploy.
  • Run the shared C++ detection tests after changing core algorithms.
  • Verify first boot, provisioning, reconnect, and recovery on physical hardware.
  • Measure detector CPU and memory cost alongside the rest of the product workload.
  • Measure motion behavior in the intended room, not only on the bench.
