Reference architecture

The runtime fits inside an ESP-IDF product. Your firmware owns the product lifecycle and ESPectre owns the sensing path.

Product and runtime ownership

YOUR FIRMWARE

Product lifecycle

Boot, Wi-Fi provisioning, connectivity policy, storage, OTA, UI, and the action taken when sensing state changes.

ESPECTRE

Sensing lifecycle

CSI capture, temporal admission, calibration, detector evaluation, readiness, snapshots, diagnostics, and runtime events.

BOUNDARY

One controller and one listener

RuntimeFrontendController accepts configuration and controls. IRuntimeListener delivers state changes and faults.

Lifecycle and task ownership

Join Wi-Fiproduct task
setup(listener)start sensing
loop()deliver events
shutdown()release runtime

Call setup(), loop(), runtime controls, and shutdown() from one owner task. Listener callbacks run on that same task and must remain bounded; queue network publication, NVS writes, and other blocking work for another task.

A failed setup() leaves the controller unconfigured so the product can correct the configuration and retry. Control calls return false when a value is invalid, a capability is unavailable, or the backend refuses the change. Asynchronous runtime failures arrive through on_runtime_fault().

Three-layer architecture

Dependencies point in one direction: frontend → runtime → core. A product normally replaces the frontend and reuses the lower two layers.

Frontend src/cpp/frontend/
Maps sensing into product behavior, protocols, and ecosystem APIs. ESPHome, Native, and Matter are maintained references, not a supported library surface.
Runtime src/cpp/runtime/
Defines lifecycle, calibration, snapshots, events, diagnostics, capabilities, and controls. ESP-IDF implementations live under runtime/esp_idf/.
Core src/cpp/core/
Owns CSI format, conditioning, features, and the Lightweight and High Accuracy detectors. It is portable C++17 and requires no ESP-IDF runtime.

Building a runtime for another platform

A platform port implements IEspectreRuntime, feeds normalized CSI into the shared core, preserves evaluation and readiness semantics, and delivers listener events from its owner task. The shipped RuntimeFrontendController currently constructs ESP-IDF backends directly, so a new platform also needs its own controller or factory.

Arduino on ESP32Feasible as a new adapter over Arduino-ESP32 and its ESP-IDF CSI facilities when the build provides C++17. No Arduino runtime is shipped today.
Raspberry Pi / LinuxRequires a Wi-Fi chipset, firmware, and driver that expose usable CSI. Standard Linux Wi-Fi connectivity alone is not enough.
