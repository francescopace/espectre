PRODUCT FIT

Confirm the integration boundary first.

The supported path targets ESP-IDF products that can vendor and rebuild the SDK sources with their own firmware.

Toolchain
ESP-IDF 5.5 or later and C++17. Repository firmware currently builds with ESP-IDF 5.5.5.
Hardware
ESP32, ESP32-S2, ESP32-S3, ESP32-C3, ESP32-C5, and ESP32-C6 with standard single-antenna Wi-Fi CSI.
Validated sensing
Published detector evidence uses 2.4 GHz HT20 CSI with HT-LTF. The runtime selects lltf20 on the original ESP32, vht20 on a VHT-capable 5 GHz association, and ht20 otherwise. The active read-only profile appears in info. Detection quality at 5 GHz is not yet characterized.
Delivery model
A versioned C++ source SDK, ready to vendor as an ESP-IDF component. ESPectre is compiled together with your firmware; precompiled libraries are not provided.
Compatibility
Final releases follow Semantic Versioning for the documented C++ source API. The SDK does not promise a stable binary ABI.
Licensing
GPLv3 for open-source firmware, with separate commercial terms available for eligible proprietary integrations. Review licensing.
QUICK START

From source bundle to motion events.

These three steps cover the recommended full-runtime integration.

01

Add the SDK

Extract the release bundle, then copy its src/cpp/ directory to components/espectre/. The copied directory is the ESP-IDF component root:

# main/CMakeLists.txt
idf_component_register(
  SRCS "main.cpp"
  REQUIRES espectre
)

The sensing runtime is always built. Direct HTTP, MQTT, provisioning, and OTA sources remain disabled until selected in menuconfig.

02

Drive the runtime

Set it up after the default station and event loop exist, preferably before association. An already connected station is restored from its current IP state. Call loop() continuously, and queue the events your product needs:

#include "espectre_sdk.h"

class ProductFrontend : public espectre::IRuntimeListener {
 public:
  bool setup() {
    runtime_.set_config(
        espectre::make_runtime_sensing_config_from_kconfig());
    return runtime_.setup(this);
  }

  void loop() { runtime_.loop(); }

  void on_motion_state_changed(
      const espectre::RuntimeSnapshot& snapshot) override {
    if (!snapshot.ready_to_publish) return;
    enqueue_motion(snapshot.motion_state == espectre::MotionState::MOTION);
  }

 private:
  void enqueue_motion(bool motion);
  espectre::RuntimeFrontendController runtime_;
};

Shared logging is optional. Register an espectre::LogSink before runtime_.setup() when the product needs SDK messages; otherwise, the shared layers remain silent.

03

Keep the runtime contracts

  • Publish only when snapshot.ready_to_publish is true.
  • Run setup(), loop(), and shutdown() on one task.
  • Keep listener callbacks bounded and non-blocking; queue network and storage work elsewhere.
  • Check capabilities() before exposing optional runtime controls.
INTEGRATION PATHS

Choose the highest layer that fits.

Lower layers expose more control, but transfer lifecycle, timing, and sensing responsibilities to your firmware.

Recommended

Full runtime

Your firmware owns boot, Wi-Fi, provisioning, OTA, and product behavior. ESPectre owns CSI capture, calibration, detection, and events.

ESP-IDF 5.5+ · C++17
Advanced

Core only

Use this only when your firmware already captures and normalizes CSI. You also own evaluation cadence, readiness, gap reset, and hit filtering.

Portable C++17
Platform port

New runtime

Implement IEspectreRuntime when another platform owns CSI capture and lifecycle while the shared core and event contracts remain useful.

Arduino or Linux · not shipped today
ALTERNATIVE RUNTIME

Micro-ESPectre supports on-device R&D.

Micro-ESPectre uses the ESP32 CSI support contributed to mainline MicroPython for Lightweight sensing, read-only Direct monitoring, and detector parity work. It remains a maintained R&D runtime, not a stable embeddable SDK.
